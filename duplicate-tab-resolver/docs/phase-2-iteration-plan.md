# Duplicate Tab Resolver 二期迭代规划

## 1. 文档目标

这份文档用于在现有一期 MVP 的基础上，明确二期应该继续做什么。

它不是实现文档，而是一个面向产品和技术落地的迭代规划，重点回答下面几个问题：

- 现有一期已经做到什么程度
- 原始 plan 文档里的二期目标是什么
- 结合当前实现现状，二期应该如何调整范围
- 二期建议优先做哪些能力
- 二期的开发顺序和验收标准是什么

## 2. 当前一期现状

结合当前插件目录下已经实现的能力，一期实际上已经覆盖了下面这些内容：

- Manifest V3 插件骨架已完成
- `service worker` 已接入自动去重主流程
- 支持完整 URL 严格匹配
- 支持 3 个默认动作：
  - `activate_existing_close_new`
  - `close_old_keep_new`
  - `keep_both`
- 支持设置页修改默认动作
- 支持黑名单规则
- 支持基础 URL 过滤
- 支持基础并发保护

这意味着：

> 原始 plan 中属于一期的核心能力，已经基本具备可继续迭代的基础。

## 3. 原始 plan 文档中对二期的定义

最初的 plan 文档里，二期被定义为“体验增强”，主要包含：

- 最近一次自动处理记录
- 撤销操作
- 白名单域名
- 黑名单域名

但现在和最初规划相比，有一个变化：

- 黑名单已经被提前纳入一期并实现

所以如果继续照搬原始二期范围，会出现重复。

## 4. 结合当前现状后的二期调整

基于当前实现，二期建议调整为下面这 4 个主题：

1. 自动处理记录
2. 撤销最近一次自动处理
3. 白名单规则
4. 设置页体验增强

其中：

- `自动处理记录` 和 `撤销` 是二期的核心价值
- `白名单` 是规则体系补全
- `设置页体验增强` 是为了让前面 3 项真正可用

## 5. 二期的核心目标

二期不再追求“只是能处理重复标签页”，而是要解决下面这个问题：

> 用户知道插件刚才做了什么，并且在觉得不合适时，有机会恢复最近一次自动处理结果。

这会明显提升用户信任感。

因为一期虽然已经能自动处理，但从用户角度看还有两个问题：

- 插件动作是“发生了”，但用户不一定知道具体发生了什么
- 如果默认动作不符合当下场景，用户没有回退手段

这两个问题，正是二期最应该优先解决的。

## 6. 二期功能范围建议

### 必做功能

建议二期必做下面 4 项：

#### 6.1 最近自动处理记录

目标：

- 记录最近一次或最近若干次自动处理事件
- 让用户能在设置页看到插件最近做了什么

建议记录的信息：

- 处理时间
- 新标签页 URL
- 旧标签页 URL
- 执行的策略
- 被关闭的 tab id
- 被激活的 tab id
- 是否执行成功

建议一期先做“最近 10 条记录”即可，不需要复杂历史系统。

#### 6.2 撤销最近一次自动处理

目标：

- 在有限范围内，允许用户恢复最近一次自动处理结果

建议支持的撤销范围：

- 仅支持撤销最近一次成功处理记录
- 仅支持在短时间窗口内撤销，例如 30 秒或 60 秒内

建议的撤销能力边界：

- 对于 `activate_existing_close_new`
  - 撤销时重新打开被关闭的新标签页 URL
  - 尝试切回原先上下文
- 对于 `close_old_keep_new`
  - 撤销时重新打开被关闭的旧标签页 URL
- 对于 `keep_both`
  - 无需撤销

这里要提前接受一个现实：

> 撤销不可能做到“100% 恢复现场”，更合理的目标是“恢复被关闭页面的访问入口”。

也就是说，二期撤销更像“恢复页面”，而不是“完整恢复浏览器当时所有状态”。

#### 6.3 白名单规则

目标：

- 允许用户声明某些网站始终不参与自动处理
- 或者更准确地说，允许某些网站始终保留重复页

二期建议的白名单语义：

- 命中白名单的 URL，直接跳过去重流程
- 白名单优先级高于黑名单

建议支持的白名单格式与黑名单保持一致：

- `example.com`
- `*.example.com`
- `localhost`
- `127.0.0.1`

这样好处是：

- 学习成本低
- 规则实现可复用
- UI 设计一致

#### 6.4 设置页体验增强

目标：

- 让记录、撤销、白名单真正可配置、可理解、可操作

建议新增的设置页能力：

- 白名单编辑区域
- 最近处理记录面板
- “撤销最近一次处理”按钮
- 更清晰的说明文案

## 7. 二期不建议做的内容

为了避免二期再次膨胀，建议先不做下面这些内容：

- 忽略 query / hash 的高级比较
- 只在当前窗口内去重
- 每个站点单独配置策略
- 页面内提示条
- 浏览器通知
- 批量历史归档和搜索
- 完整统计面板

这些能力更适合三期或更后面。

原因很简单：

- 它们不是当前最阻塞用户体验的问题
- 它们会快速增加配置复杂度
- 会稀释二期对“可理解、可回退”的主目标

## 8. 二期的功能优先级

建议按下面优先级推进：

### P0

- 最近自动处理记录
- 撤销最近一次自动处理

### P1

- 白名单规则
- 设置页支持白名单输入

### P2

- 记录展示体验优化
- 错误文案优化
- 记录清空按钮

这样安排的原因是：

- 没有记录，就谈不上撤销体验
- 没有撤销，自动处理在用户心里仍然偏“黑盒”
- 白名单虽然重要，但优先级略低于“可观测 + 可回退”

## 9. 二期技术设计方向

### 9.1 数据模型扩展

当前设置结构大致是：

```text
settings = {
  enabled,
  duplicateStrategy,
  blacklist,
  scope
}
```

二期建议扩展为：

```text
settings = {
  enabled,
  duplicateStrategy,
  blacklist,
  whitelist,
  scope,
  undoWindowSeconds,
  maxActionHistory
}
```

同时新增独立的历史记录存储：

```text
actionHistory = [
  {
    id,
    timestamp,
    strategy,
    currentTabUrl,
    existingTabUrl,
    closedTabUrl,
    activatedTabId,
    closedTabId,
    status,
    undoableUntil
  }
]
```

### 9.2 存储策略建议

建议仍然使用 `chrome.storage.local`。

原因：

- 当前数据量很小
- 不需要后端
- 配置和历史统一存在本地最简单

但要注意两点：

- 历史记录要限制数量，例如最多保留 10 条或 20 条
- 每次写入要走统一的标准化逻辑

## 10. 二期规则优先级建议

引入白名单之后，需要把规则优先级写死，否则后面容易混乱。

建议优先级如下：

1. 插件总开关关闭
   - 直接跳过
2. URL 不可处理
   - 直接跳过
3. 命中白名单
   - 直接跳过自动处理
4. 命中黑名单
   - 直接跳过自动处理
5. 进入重复检测

### 为什么白名单优先于黑名单

因为白名单更像是用户明确表达的“放行意图”。

如果一个站点同时出现在白名单和黑名单：

- 应按白名单处理

这样更符合用户心理预期。

## 11. 二期处理链路建议

建议把后台处理流程升级为：

```text
标签页 URL 更新
    ↓
读取 settings
    ↓
判断插件是否启用
    ↓
判断 URL 是否可处理
    ↓
判断是否命中白名单
    ↓
判断是否命中黑名单
    ↓
检测重复标签页
    ↓
执行默认策略
    ↓
生成一条 action record
    ↓
写入 action history
    ↓
如果策略可撤销，则设置 undoableUntil
```

## 12. 撤销能力的技术边界

撤销是二期里最容易被高估的功能，所以必须先定义边界。

### 能做的

- 重新打开被关闭的 URL
- 恢复一个“最近被处理的入口”
- 在设置页里显式触发一次撤销

### 不能保证的

- 恢复页面滚动位置
- 恢复页面表单输入状态
- 恢复单页应用内部状态
- 恢复原始 tab 的完整历史栈

所以二期文案应避免写成“完全恢复”，而应写成：

> 撤销最近一次自动处理，重新打开被关闭的页面。

## 13. 设置页改版建议

当前设置页只有最基础的配置能力，二期建议拆成 3 个区块：

### 区块 1：基础设置

- 插件总开关
- 默认策略
- 撤销时间窗口

### 区块 2：规则设置

- 白名单输入框
- 黑名单输入框
- 规则说明

### 区块 3：最近操作

- 最近处理记录列表
- 撤销最近一次处理按钮
- 清空记录按钮

这样的好处是：

- 信息组织更清晰
- 用户能理解“设置”和“最近发生了什么”是两件事
- 未来继续加站点规则时，也有位置可以扩展

## 14. 二期开发顺序建议

建议严格按这个顺序推进：

1. 扩展设置模型，加入白名单和历史配置项
2. 增加历史记录读写模块
3. 在策略执行成功后写入 action record
4. 在设置页展示最近处理记录
5. 实现“撤销最近一次处理”
6. 实现白名单匹配逻辑
7. 在设置页加入白名单编辑区
8. 做边界验证和文案优化

### 为什么先做记录，再做撤销

因为撤销的前提是：

- 你得知道刚才处理了什么

如果没有一套稳定的记录结构，撤销逻辑会变得很脆弱。

## 15. 二期验收标准建议

二期完成时，至少应满足下面这些验收标准：

### 记录能力

- 每次自动处理后都能生成记录
- 设置页能展示最近记录
- 记录数量超限时会淘汰旧记录

### 撤销能力

- 对最近一次可撤销记录，可以点击撤销
- 撤销后能重新打开被关闭的 URL
- 超过撤销时间窗口后，按钮不可用或提示不可撤销

### 白名单能力

- 命中白名单的网站不会进入自动处理
- 白名单格式与黑名单一致
- 白名单优先于黑名单

### 设置页体验

- 新增字段可保存并回显
- 用户能理解白名单、黑名单、最近记录和撤销的关系

## 16. 二期主要风险

### 风险 1：撤销语义和用户预期不一致

解决建议：

- 在文案里明确“重新打开页面”，而不是“完全恢复”

### 风险 2：历史记录结构设计得太重

解决建议：

- 二期只保留最近少量记录
- 不做复杂筛选、分页和统计

### 风险 3：白名单和黑名单冲突

解决建议：

- 明确白名单优先
- 在设置页说明这一点

### 风险 4：设置页过于复杂

解决建议：

- 按区块拆分
- 控制字段数量
- 不在二期引入站点级复杂策略

## 17. 我建议的二期最终定义

如果把二期压缩成一句话，我建议这样定义：

> 二期重点不是让插件“更聪明”，而是让插件“更可理解、可回退、可定制”。

对应到具体能力，就是：

- 记录最近处理结果
- 支持撤销最近一次自动处理
- 加入白名单规则
- 把设置页升级成可解释这些行为的控制面板
