# Chrome 重复标签页处理器一期技术方案

## 1. 文档目标

这份文档不是代码实现说明，而是第一期可开工版本的技术设计文档。

目标是把下面这件事说清楚：

> 用一个 Manifest V3 的 Chrome 插件，在检测到“当前打开的 URL 已经存在于其他标签页中”时，按照用户预设的默认策略自动处理；第一期同时支持黑名单域名。

这个文档覆盖：

- 一期范围和非目标
- 架构拆分
- 事件流
- 权限设计
- 设置项和存储结构
- 重复检测规则
- 黑名单规则
- 边界条件
- 开发顺序

## 2. 一期目标

### 功能目标

第一期实现以下能力：

- 监听普通网页标签页的 URL 变化
- 检测是否存在“完整 URL 完全一致”的其他标签页
- 根据默认策略自动处理重复标签页
- 提供设置页修改默认策略
- 提供黑名单配置，命中黑名单时不参与检测和处理
- 排除浏览器内部页、插件页、空白页等非目标页面

### 支持的默认策略

一期支持 3 种处理策略：

1. `activate_existing_close_new`
   - 激活旧标签页，并关闭当前新标签页
2. `close_old_keep_new`
   - 关闭旧标签页，保留当前新标签页
3. `keep_both`
   - 不自动处理，仅放行当前重复标签页

### 一期不做

为了控制复杂度，一期不做以下内容：

- 每次重复时弹窗询问
- 页面内浮层提示
- 撤销操作
- 白名单规则
- 忽略 query / hash 的高级比较
- 站点级差异化策略
- 自动统计和历史面板

## 3. 产品规则先定死

技术方案要稳定，前提是产品规则先明确。

一期建议固定以下规则：

### 重复定义

- 仅当两个标签页的完整 URL 字符串完全一致时，判定为重复
- 比较项包括协议、域名、路径、query、hash

### 旧标签页定义

- 当前触发检测的标签页视为“新标签页”
- 与其 URL 相同且 `tabId` 不同的已存在标签页视为候选“旧标签页”
- 若存在多个候选，则取“最早创建或最先查到的那个标签页”作为旧标签页

### 黑名单定义

- 黑名单按域名规则匹配
- 命中黑名单的网站，不参与重复检测，也不做任何自动处理
- 一期不支持更复杂的 URL 正则规则，先控制为简单、可解释的规则模型

## 4. 整体架构

一期建议只做两个核心模块：

- 后台事件处理：`service worker`
- 用户设置页面：`options page`

不需要：

- `popup`
- `content script`
- 后端服务

### 架构图

```text
┌─────────────────────────────────────────────┐
│                options page                │
│ 修改默认策略 / 修改黑名单 / 保存到 storage │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│            chrome.storage.local            │
│ 保存用户配置                                │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│              service worker                │
│ 监听 tabs 事件 -> 读取配置 -> 执行去重逻辑   │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│                chrome.tabs                 │
│ 查询标签页 / 激活标签页 / 关闭标签页         │
└─────────────────────────────────────────────┘
```

## 5. 为什么选这个架构

这样拆分的原因很简单：

- 去重逻辑本质上是浏览器事件驱动，适合放在 `service worker`
- 配置是低频编辑场景，适合放在 `options page`
- 不做页面注入，可以减少权限和兼容性问题
- 不做 popup，可以避免“用户不点图标就看不到状态”的问题

对于你这个插件，一期最重要的是：

> 后台逻辑足够稳定、规则足够清晰、设置足够简单。

## 6. 目录结构建议

虽然这里还不写代码，但建议从一开始就按下面的结构组织：

```text
extension/
├── manifest.json
├── src/
│   ├── background/
│   │   ├── service-worker.ts
│   │   ├── duplicate-detector.ts
│   │   ├── tab-actions.ts
│   │   ├── settings-store.ts
│   │   └── url-rules.ts
│   ├── options/

│   │   ├── options.ts
│   │   └── options.css
│   └── shared/
│       ├── types.ts
│       ├── constants.ts
│       └── validators.ts
└── assets/
    └── icons/
```

### 模块职责建议

#### `service-worker.ts`

- 注册并响应标签页事件
- 串联整个处理流程

#### `duplicate-detector.ts`

- 输入当前 tab 和配置
- 查询候选标签页
- 返回是否重复、命中的旧标签页是谁

#### `tab-actions.ts`

- 封装对 `chrome.tabs` 的操作
- 激活 tab
- 关闭 tab
- 切换窗口焦点

#### `settings-store.ts`

- 读取和保存配置
- 补默认值
- 做基础合法性校验

#### `url-rules.ts`

- 判断是否为可处理 URL
- 判断是否命中黑名单
- 统一处理 URL 解析逻辑

#### `types.ts`

- 放设置项类型、策略枚举、黑名单结构等共享定义

## 7. 核心权限设计

一期应尽量少权限。

### 建议权限

- `tabs`
  - 用于读取标签页 URL、查询标签页列表、激活和关闭标签页
- `storage`
  - 用于保存默认策略和黑名单配置

### 不建议一期申请的权限

- `notifications`
  - 一期没有提示需求
- `scripting`
  - 一期不做页面注入
- `activeTab`
  - 这个插件是全局监听行为，不是用户手动点一下才生效的临时动作

### 关于 host 权限

一期如果仅依赖 `tabs` + 标签页 URL 读取能力，通常可以先保持最小化设计，不主动扩展到页面注入相关 host 权限。

设计原则是：

> 先满足“标签页管理”，不要为了未来可能的页面 UI 能力提前扩大权限。

## 8. manifest 设计要点

虽然这里不直接写 `manifest.json`，但第一期至少要包含这些概念：

- `manifest_version: 3`
- 插件名称、版本、描述
- `background.service_worker`
- `options_page` 或 `options_ui`
- `permissions`

### 关键点

- 后台逻辑入口放在 `service worker`
- 设置页面必须能独立打开和保存配置
- 如果后续用 TypeScript 或构建工具，最终打包结果仍要落成 Chrome 可识别的静态文件

## 9. 配置模型设计

一期建议把所有配置收拢成一个统一对象，存到 `chrome.storage.local`。

### 配置对象建议

```text
settings = {
  enabled: true,
  duplicateStrategy: "activate_existing_close_new",
  blacklist: [
    "localhost",
    "127.0.0.1",
    "*.example.com"
  ],
  scope: "all_windows"
}
```

### 字段说明

#### `enabled`

- 是否启用插件总开关
- 便于用户临时关闭整个去重功能

#### `duplicateStrategy`

- 默认动作
- 可选值：
  - `activate_existing_close_new`
  - `close_old_keep_new`
  - `keep_both`

#### `blacklist`

- 黑名单规则列表
- 一期建议按“域名模式”存储，而不是正则表达式

#### `scope`

- 去重范围
- 一期建议固定支持 `all_windows`
- 即查找所有浏览器窗口中的重复标签页

虽然 `scope` 只有一个值，但我仍建议保留这个字段，方便未来扩展为“仅当前窗口”。

## 10. 黑名单规则设计

你已经明确提出一期就要加黑名单，所以这里需要先把规则做得可解释、可维护。

### 一期支持的黑名单格式

建议支持这 3 类：

1. 精确域名
   - `example.com`
2. 泛域名匹配
   - `*.example.com`
3. 本地开发常见域
   - `localhost`
   - `127.0.0.1`

### 一期不支持的黑名单格式

- 完整正则表达式
- 按路径匹配
- 按 query 匹配
- 协议级复杂判断

### 匹配规则建议

当一个 URL 被解析后，取其 `hostname` 来做黑名单判断：

- 若规则是 `example.com`
  - 只匹配 `example.com`
  - 不自动匹配 `a.example.com`
- 若规则是 `*.example.com`
  - 匹配 `a.example.com`、`b.example.com`
  - 是否匹配根域名 `example.com`，建议第一期明确为“不匹配”

这样规则更清楚，也更不容易产生误会。

### 为什么黑名单按 hostname 而不是完整 URL

因为用户配置黑名单时，通常想表达的是：

- “这个网站我不想管”

而不是：

- “这个网站的某个具体 URL 我不想管”

从产品直觉和配置简洁性来看，hostname 黑名单更合适。

## 11. URL 处理规则

一期最关键的是把 URL 处理边界先守住。

### 可处理 URL

建议只处理：

- `http://`
- `https://`

### 不处理的 URL

建议直接跳过：

- `chrome://`
- `chrome-extension://`
- `devtools://`
- `about:blank`
- `file://`
- `view-source:`
- 空 URL

### 为什么 `file://` 一期也先跳过

本地文件页虽然技术上也可能比较，但它不属于这个插件最核心的网页场景，而且会带来更多权限和特殊行为讨论。

第一期应该优先保证普通 Web 页面逻辑稳定。

## 12. 事件监听策略

一期推荐主要依赖 `tabs.onUpdated`。

### 原因

当用户新开一个标签页时：

- 刚创建时 URL 可能还不是最终值
- 可能先是空白页，再跳到目标 URL

所以直接监听“创建”并不够准确。

### 建议监听时机

监听 `tabs.onUpdated`，重点关注：

- `changeInfo.url` 出现时
- 或 tab 更新为目标 URL 后

### 可选补充监听

如果后续发现某些网站场景下仅靠 `onUpdated` 不稳，可以再评估补充：

- `tabs.onCreated`
- `tabs.onActivated`
- `webNavigation`

但第一期建议先克制，只用一个主事件源，把复杂度压低。

## 13. 去重处理主流程

下面是一条建议的标准处理链路：

```text
标签页 URL 更新
    ↓
判断插件总开关是否启用
    ↓
判断 URL 是否属于可处理协议
    ↓
解析 hostname
    ↓
判断是否命中黑名单
    ↓
查询所有标签页
    ↓
查找 URL 完全相同且 tabId 不同的候选 tab
    ↓
若没有候选，结束
    ↓
选定旧标签页
    ↓
根据默认策略执行动作
    ↓
结束
```

## 14. 去重算法建议

一期不需要做复杂索引，直接按事件触发时临时查询即可。

### 输入

- 当前触发事件的 `tabId`
- 当前 tab 的完整 URL
- 当前用户设置

### 检测步骤

1. 读取当前 tab 的 URL
2. 校验是否可处理
3. 查询所有已打开标签页
4. 过滤掉：
   - 自己
   - URL 为空的 tab
   - 不可处理协议 tab
   - 命中黑名单的 tab
5. 在剩余 tab 中找出与当前 URL 完全一致的 tab
6. 若存在多个，选定一个最早候选作为旧标签页

### 为什么一期不做内存索引

理论上可以维护一个 `url -> tabIds` 的映射缓存，但第一期不建议这么做，因为：

- service worker 不是持久常驻
- 标签页状态变化很多
- 缓存失效处理容易出错
- 事件触发时临时查询对这个规模完全足够

结论很简单：

> 用最直接的查询换稳定性，一期是值得的。

## 15. 3 种策略的具体执行规则

### 策略 A：`activate_existing_close_new`

执行动作：

1. 找到旧标签页
2. 激活旧标签页
3. 如果旧标签页不在当前窗口，切换到对应窗口
4. 关闭当前新标签页

### 策略 B：`close_old_keep_new`

执行动作：

1. 找到旧标签页
2. 关闭旧标签页
3. 保留当前新标签页

### 策略 C：`keep_both`

执行动作：

1. 检测到重复
2. 不做任何 tab 操作
3. 直接结束

### 一期策略执行原则

- 不做二次确认
- 不做额外提示
- 出错时静默失败即可，但开发阶段需要日志

## 16. 并发与重复触发问题

这是一期必须提前考虑的技术风险。

### 问题 1：同一个 tab 可能触发多次更新

一个页面加载过程中，`onUpdated` 可能触发多次。

这可能导致：

- 重复检测多次
- 同一个新标签页被重复处理

### 解决建议

在 `service worker` 内维护一个短生命周期的“处理中 tab 集合”：

- 某个 `tabId` 开始处理时加入集合
- 处理完成或失败后移出集合
- 如果同一个 `tabId` 在处理中再次触发，则直接跳过

### 问题 2：两个标签页几乎同时打开同一 URL

这种场景下可能出现竞争：

- A 把 B 视为旧 tab
- B 又把 A 视为旧 tab

### 解决建议

一期采用简单规则：

- 总是把“当前事件触发的 tab”视为新 tab
- 只允许当前 tab 对其他 tab 做决策
- 旧 tab 选择时优先取更早存在的 tab

如果仍出现边缘竞争，也优先接受“偶发保留两个”的结果，而不要为了一期做复杂锁。

## 17. 错误处理策略

Chrome 插件操作标签页时，常见失败情况包括：

- 某个候选 tab 在查询后又被用户关闭
- 某个窗口已不存在
- 标签页激活或关闭时 API 返回错误

### 一期建议

- 对关键 API 调用做 `try/catch`
- 如果执行失败，直接结束本次处理
- 不影响后续事件
- 开发阶段保留日志，生产阶段减少噪音

这个插件是辅助型工具，不是关键业务系统，所以容错策略应偏保守：

> 单次失败可以接受，不要因为一次异常让整个插件状态混乱。

## 18. 设置页设计建议

一期设置页只需要够用，不需要复杂。

### 页面内容建议

- 一个总开关
- 一个默认策略选择器
- 一个黑名单编辑区域
- 一个保存按钮
- 一个简单说明区

### 黑名单输入方式建议

最简单的交互是：

- 多行文本框
- 每行一条规则

例如：

```text
localhost
127.0.0.1
*.internal.example.com
example.com
```

### 为什么不用复杂表单组件

因为第一期重点不在配置管理体验，而在去重逻辑本身。

多行文本框的优点是：

- 实现最简单
- 用户容易复制粘贴
- 存储结构也直接对应字符串数组

## 19. 设置页校验规则

虽然交互可以简单，但保存前还是要做基础校验。

### 建议校验内容

- 空行自动忽略
- 去掉每行首尾空格
- 规则统一转小写
- 去重
- 拒绝明显非法规则

### 非法规则示例

- `http://example.com`
  - 黑名单只接受域名模式，不接受完整 URL
- `/abc/`
  - 一期不支持正则
- `a*b.example.com`
  - 一期只支持最左侧的 `*.` 泛匹配

### 保存后的标准化结果

建议写入存储前做标准化：

- 输入：`  EXAMPLE.COM `
- 存储：`example.com`

这样后台匹配逻辑会更简单。

## 21. 日志与调试建议

虽然面向用户的一期没有提示，但开发期需要有足够的可观测性。

### 建议日志点

- 插件启动
- 配置读取结果
- URL 被跳过的原因
- 命中黑名单
- 发现重复 tab
- 执行了哪种策略
- API 调用失败

### 为什么日志重要

Chrome 插件尤其是 MV3 下的 `service worker`，调试体验和普通前端页面不一样。

如果没有结构化日志，你会很难分辨：

- 是事件没触发
- 是 URL 被过滤了
- 是命中了黑名单
- 还是策略执行失败了

## 22. 一期测试重点

虽然这里不写测试代码，但建议从一开始就按下面场景验证。

### 基础功能

- 新开一个 URL，且不存在重复 tab
- 新开一个 URL，且已存在重复 tab
- 3 种默认策略分别验证一次

### 黑名单场景

- 命中精确域名黑名单
- 命中泛域名黑名单
- 根域名与泛域名匹配差异验证
- `localhost` 与 `127.0.0.1` 验证

### 边界场景

- `about:blank`
- `chrome://settings`
- 标签页快速连续跳转
- 同一 URL 在不同窗口中重复
- 用户在插件处理过程中手动关闭 tab

## 23. 一期的已知限制

这不是缺陷，而是有意控制范围。

### 限制 1

只按完整 URL 字符串比较，意味着：

- `https://a.com/page?a=1`
- `https://a.com/page?a=2`

会被视为不同页面。

### 限制 2

黑名单只支持域名级规则，不支持路径级或正则规则。

### 限制 3

不做用户可见提示，因此：

- 用户只能通过结果感知插件行为
- 若想理解发生了什么，需要到设置页或调试日志查看

### 限制 4

对于极端并发打开同 URL 的情况，一期不保证绝对“只剩一个 tab”，但应保证不会出现明显错误行为。
